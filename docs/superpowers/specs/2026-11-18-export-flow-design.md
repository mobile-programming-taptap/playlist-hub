# 내 플레이리스트 → 다른 플랫폼 내보내기 전용 흐름 설계

작성일: 2026-11-18 · 상태: 검토 대기

## 1. 의도

변환 탭에서 내 플레이리스트를 가져와 다른 플랫폼으로 내보내는 과정이 사용자에게 너무 번거롭다. 목표는 사용자가 느끼는 불편을 줄이고 사용감을 개선하는 것이다.

현재 내보내기는 가져오기 흐름의 맨 끝에 있다. 사용자는 다음 순서를 거친다.

1. 서비스 선택
2. 목록 체크
3. 가져오기 결과
4. 곡 확인 (곡마다 편집 칸이 있음)
5. 화면 맨 아래에서 대상 선택
6. 매칭
7. 곡마다 후보 대화상자 열기
8. 목록 이름 재입력
9. 확인 창
10. 순번만 보이는 결과

이 설계는 "목록 고르기 → 대상 고르기 → 확인 필요한 곡만 보기 → 보내기"라는 짧은 전용 흐름을 만든다.

## 2. 목표 · 비목표 · 실패 조건

**목표**
- 내 플레이리스트 화면에서 바로 "다른 플랫폼으로 보내기"를 시작한다.
- 곡 편집 화면을 거치지 않고 매칭으로 넘어간다.
- 검수 화면에서는 사용자가 판단해야 하는 곡만 위에 보인다.
- 버튼 하나로 전송하고, 결과를 곡 이름으로 보여준다.
- 목록 이름은 한 번만 확인한다.

**비목표 (이번 범위 밖)**
- 여러 목록 한 번에 내보내기. 1차는 한 목록씩만 보낸다.
- 백엔드 API 변경
- 영상 변환(타임라인)에서 내보내는 흐름. 기존 경로를 유지한다.
- 기존 "가져온 곡 확인 → 대상 플랫폼의 곡 후보 찾기" 경로 제거. 유지한다.

**실패로 보는 경우 (기술적으로 동작하더라도)**
- 사용자 확인 없이 '확인 필요' 곡이 전송된다.
  - 명세 F-09: AI 판단만으로 곡을 확정하지 않는다.
  - 명세 F-08·11절: 사용자가 검수하고 전송을 실행한다.
- 매칭이 끝나지 않았는데 보내기 버튼이 눌린다.
- 화면을 돌리거나, 시스템이 백그라운드에서 앱을 종료했다가 복원했을 때 진행 상태를 잃는다.
  - 범위는 기존 Bundle 저장·복원 경로까지다.
  - 사용자가 앱을 완전히 종료한 뒤에는 기록 화면 → 가져온 목록 → "저장된 곡 후보 검토 이어보기"로 이어갈 수 있으면 충분하다. *(내 판단)*
  - 복원 후에 자동 매칭을 다시 시작하지는 않는다. [이어서 찾기]를 보여준다.

## 3. 제약

- **노션 명세:** 검수 후 전송, 화면당 강조 동작 하나, 핵심 버튼은 하단. 로딩·실패 상태에서도 다음 행동을 제공한다.
- **서버 동작 (변경하지 않음):**
  - `POST /imports/playlists`는 곡이 있으면 앱 내 목록에 자동 저장한다. 따라서 내보내기에도 앱 내 사본이 남는다. 이 점을 결과 화면에 한 줄로 안내한다.
  - `POST /matches`는 저장 단계 없이 가져온 `items`로 바로 매칭할 수 있다.
  - 매칭은 한 번 호출에 YouTube 5곡, Spotify 20곡씩 처리하고 `nextOffset`을 돌려준다.
  - `PUT /matches/{id}`는 선택을 저장한다. `POST /transfers`는 모든 곡이 승인(선택 또는 제외)되어야 실행된다.
- **YouTube 검색 할당량:** 기본 하루 `search.list` 100회다. 긴 목록을 YouTube로 보내면 중간에 한도에 걸릴 수 있다. 실패 상태와 "이어서 찾기"가 필요하다.
- **코드 구조:** 모든 화면은 `HubActivity.java`의 `screen` 상태와 `requests.data`로 그린다. 새 상태 키는 `SAVED_TEXT` 또는 기존 저장·복원 경로에 넣어서 회전·재시작 후에도 복원되게 한다.

## 4. 고려한 방식

| 방식 | 내용 | 장단점 |
| --- | --- | --- |
| A. 동선만 다듬기 | 기존 화면을 유지하고 미리 선택, 자동 이어 찾기, 이름 한 번 입력, 결과 곡명 표시만 개선 | 작고 안전하다. 하지만 가져오기 → 곡 확인 → 매칭 → 전송의 긴 경로는 그대로다. |
| **B. 내보내기 전용 흐름 (선택)** | 라이브러리 화면에서 보내기를 시작한다. 편집 화면을 건너뛰고, 확인 필요한 곡만 위에 보여준다. | 핵심 불편(내보내기가 흐름 끝에 묻힘)을 해결한다. 검수 원칙을 유지하고, A의 개선도 대부분 포함한다. 화면과 상태가 늘어난다. |
| C. 일치 곡 자동 전송 | 일치한 곡은 묻지 않고 바로 보낸다 | 가장 빠르지만 "검수 후 전송" 명세와 충돌해서 제외했다. |

사용자가 B를 선택했다 (2026-11-18).

## 5. 확정된 흐름 (사용자 결정)

```
[내 플레이리스트]  목록 체크
   하단: [선택한 목록 앱에 저장]  [다른 플랫폼으로 보내기]
            │
            ▼ 보내기 (목록 1개 선택 시)
[대상 플랫폼 선택]  출발 플랫폼은 제외
            │
            ▼ 자동: 가져오기 → 매칭 (진행률 표시)
[보낼 곡 확인]
   새 목록 이름: [원본 이름]
   ── 확인이 필요한 곡 (3) ──
   카드마다 최상위 후보 + [이 곡으로] [다른 후보] [제외]
   ── 찾지 못한 곡 (2) · 제외됨 ──   (탭하면 다시 고를 수 있음)
   ── 자동 선택된 곡 42 ▸ ──          (펼치면 확인·변경 가능)
   하단 고정: [Spotify로 47곡 보내기]
            │
            ▼ 확인 창 → 전송
[전송 결과]  곡 이름별 성공·실패, [생성된 목록 열기], 실패 곡 [다시 보내기]
```

## 6. 세부 동작 (빌더 참고용 · 제안 포함)

**진입**
- 라이브러리 하단 버튼을 둘로 나눈다.
- "다른 플랫폼으로 보내기"는 정확히 1개를 선택했을 때만 활성화한다. 2개 이상이면 "보내기는 한 번에 한 목록씩 할 수 있어요"라고 안내한다. *(내 판단)*

**대상 선택**
- 지원 플랫폼 중 출발 플랫폼을 뺀 목록을 대화상자로 보여준다. *(내 판단)*
- 대상 계정이 연결되어 있지 않으면 기존 `authorize()` 연결 흐름을 탄다. 연결 후에는 보내기 흐름으로 돌아와야 한다. 복귀 방식은 빌더 확인이 필요하다.

**자동 진행**
- 가져오기 응답을 받으면 곧바로 `POST /matches`를 부른다. `nextOffset ≥ 0`이면 자동으로 다음 페이지를 부른다.
- 화면에는 "47곡 중 20곡 찾는 중"과 [중단]을 보여준다.
- 실패하거나 중단하면 이미 찾은 결과를 보여주고 [이어서 찾기]를 하단 주 버튼으로 둔다.
- 매칭이 끝나지 않았으면 보내기 버튼은 비활성이다.

**자동 선택 규칙**

일치한 곡을 접어 두고 확인 필요한 곡만 위에 보여주는 구조는 사용자가 B안에서 고른 핵심이다.

명세 F-09 근거:
- 매칭은 규칙 기반 점수화를 기본으로 한다.
- AI 판단만으로 확정하지 않는다.
- 애매한 결과는 사용자 확인 대상으로 둔다.

따라서 규칙 점수가 `MATCHED`인 곡은 미리 선택하고, 애매한 곡은 사용자에게 맡긴다. 전송 확인 창에 "자동 선택 N곡 포함"을 명시해서, 사용자가 전송을 실행하는 행위를 검수 완료로 본다.

아래 그룹 세부 규칙은 *(내 판단)*이다.
- `MATCHED`이고 `selected`가 있으면: 그 후보를 미리 선택한다. "자동 선택" 그룹에 접어 둔다.
- 후보가 0개면: 제외로 미리 표시한다. "찾지 못한 곡 · 제외됨" 그룹에 둔다.
- `NEEDS_REVIEW`이거나, 후보가 있는 `UNKNOWN`이면: 미리 선택하지 않는다. "확인이 필요한 곡" 그룹 맨 위에 둔다.
  - 카드에 최상위 후보와 [이 곡으로]를 보여줘서 한 번에 고를 수 있게 한다.
  - [다른 후보]는 기존 `chooseCandidate` 대화상자를 연다.
- 확인이 필요한 곡이 남아 있으면 하단 버튼을 "확인 필요 3곡 남음"으로 바꾸고 비활성한다.

**전송**
- 하단 버튼을 누르면 `PUT /matches/{id}`로 선택을 저장하고, 확인 창을 거쳐 `POST /transfers`를 부른다. 기존 `reviewSaved` 경로를 재사용한다.
- 목록 이름은 검수 화면 위쪽 한 곳에서만 받는다. 기본값은 원본 목록 이름이다.

**결과**
- 전송 결과는 리뷰 항목의 `source`로 `sourceIndex`를 곡명·아티스트로 바꿔서 표시한다.
- 성공 곡은 "N곡 전송 완료"로 접고, 실패·확인 필요 곡을 위에 보여준다.
- 결과 화면에 "앱의 내 목록에도 사본이 저장됐어요"를 한 줄로 안내한다.

**기존 경로**
- 곡 확인 화면의 "대상 플랫폼의 곡 후보 찾기"와 검수 화면은 영상 변환에서도 쓰므로 유지한다.
- 결과의 곡명 표시는 기존 결과 화면에도 적용한다. *(내 판단)*
- 매칭 자동 이어 찾기는 내보내기 흐름에만 적용한다. 영상 변환 등 기존 검수 화면은 지금처럼 [다음 곡의 후보 찾기]를 수동으로 누른다. 사용자가 모르는 사이에 YouTube 검색 한도를 다 쓰지 않게 하기 위해서다. *(내 판단)*
- 같은 목록을 다시 보내면 지금처럼 새 가져오기 작업이 생기고, 앱 내 목록 사본도 새로 생긴다.
  - 기존 `importId`를 재사용하면 원본 변경이 반영되지 않는 문제가 생겨서 이번 범위에서는 바꾸지 않는다. *(내 판단)*
  - 결과 화면의 사본 안내 문구로 사용자에게 알린다.

## 7. 빌더에게 맡기는 것

- 새 `screen` 값과 상태 키 이름, 기존 `review()`·`transfer()`를 확장할지 분리할지
- 하단 고정 버튼 구현 방식. 현재 레이아웃은 `content` 스크롤 안에 버튼을 넣는다.
- 테스트 범위. 기존 Android 계측 테스트 관례를 따른다.
- 작업 브랜치. `CLAUDE_HANDOFF.md`에 따라 정상 클론의 최신 `origin/main`에서 worktree를 만든다.
